The Strainer

The Strainer is a infinite runner mobile game for android, it's similar to games like subway surfers and temple run but with a horror game twist and a ps1 style art direction!

As the PROGRAMMER for this assignement, I'm tasked with coding all gameplay features and putting all models, textures, and animations into the game engine and getting them assembled!

Below is my Development Process where I got over the ups and downs, struggles, and things I'm proud of with the development of the project.

Status: In Development

Development Updates & Devlog

Reflection

Our development of this mobile game has finally come to an end, and I’m happy to say that not only have I learned a lot, but I’ve also improved my abilities quite a lot, I’ve learned a lot more about animation over the course of this project, as well as some of the sound systems in Unreal, along with many other things that have not only helped me get better at using Unreal, but also improved my ability to work in teams.

Over the course of this project, a lot of things went well, we got the basic gameplay loop down within the first sprint and things were smooth sailing for most of the project, I am especially proud of the effects I got for the UI, It was my first time trying to have a rough / blurry effect for my UI, the first time I’d ever had to work with trying to make my UI look NOT clean and crisp, it was certainly a challenge at the beginning, especially since before this I hadn’t gone too deep into the UI editor for Unreal, but I think this project really showed me that not only did I have what it takes to make good UI, but also that I enjoy UI creation quite a bit and I am pretty good at it, I learned how to recreate the old VHS camcorder aesthetic pretty well, I even got the blur of the text down where I could, which really added to the style and the overall feeling of the game.


UI Examples:


Another thing that went really well was how I dealt with sound effects and music. In one of my previous sprint reviews I talked about some of my new experiences mixing my own sound effects, but using existing audio completely unrelated to what I needed and mixing it to fix what I was looking for, and this ended up working out perfectly, making all of my sound effects turn out great and really fit what I was looking for, but the thing I’m most proud of is the music, I had a friend work on it but when implementing it into Unreal, I found that the basic unreal engine sound system really wasn’t what I was looking for, so after a bit of digging I ended up running into the Metasound system, which was honestly what I was looking for in a sound system for a long time, instead of playing sounds and being done with them like the only sound system, Metasound lets me have them as a living sound I can access during runtime, which really helped me do some super cool things with the music that I am very proud of, and overall helped me grow my knowledge about Unreal Engine


Music Code:


On the other hand, some things definitely didn’t do good, the thing that was probably the worst for us was underestimating the engine and how many problems it would cause when we built to mobile. I definitely mentioned this before in earlier sprint reviews but originally, we didn’t anticipate any issues, since I’d had lots of experience creating builds for Unreal, and while me and my team figured it’d be a little bit different, we didn’t anticipate just HOW different it’d be, the first issue we had was getting the build to even work, which took me a few days and definitely wasn’t as simple as the few button clicks that building for Windows was. It was hard to learn the pipeline of setting up android studio and getting all the files to work properly.

After, when we finally got the build working, we ran into a plethora of issues regarding rending and lighting in the scene, since Unreal, despite making advances for Mobile, definitely isn’t built for it, leading to a lot of issues with things that worked perfectly fine on computer, such as Post Processing, Skeletal Rendering, and Lighting, all of which gave us issues that took multiple sprints and multiple people to fix, which led us to the unfortunate situation of having to cut my VHS post processing effect that I worked very hard on.

If I had all of this retrospective when starting the project, I would’ve probably prioritized getting the build working and ironing out all of the build errors long before which did, I’d start working on getting a test build set up as early as the first sprint, then build after every major system was added so that we could stomp out bugs and issues as soon as they popped up and we wouldn’t have to deal with spending a lot of time solving them and could focus mostly on coding the actual game and then fixing them as they came up, letting us use much less time overall.

Overall, this project was quite the learning experience, I’m pretty proud of what we made but there is plenty of room for improvement with my next project!

Sprint #6

As we reach the end of our Game’s development cycle and our sprints, our point count has been slowing down a little bit, but this is mostly thanks to us finishing up all the features and models and just focusing on bugs and implementing models. I got 11 points done this sprint, as well as finishing up every single last piece of programming, which thankfully only leaves us with a little bit of implementation to do, and bug fixing, for our last sprint, leaving us with a very chill and empty final sprint.

One of the main things that I did this sprint was working on some of the final UI that was needed and implementing final playtest feedback from our most recent playtest, however what I put the most work into was the respawn screen, a few of our playtesters didn’t enjoy having to go back to the main menu to play another run, so we moved to implement a respawn screen, however we had a small issue where, because of how I coded the intro, adding in respawns without reloading the level created a whole plethora of issues that took forever trying to fix. At first I tried to just get around these issues and account for them, but it felt like every time I did that it broke something else, so eventually I just decided to sort of ‘fake it’ by reloading the level and using booleans to skip past all the introduction and main menu events, which ended up working out really well and fixed pretty much every issue I had.


Respawn Page:


Another big thing I worked on was the pause menu while playing, I honestly can’t believe took me so long to even think of a pause menu, luckily it was much easier than the respawning system and took a lot less time, which definitely helped keep me motivated and left me time to focus on other things.


Pause Menu:


Something I worked on that was a little strange was remaking some of our animation systems, it may not seem like a big deal but for a little bit we were having a small issue where the sliding animation wouldn’t play every time if you were spamming slides, which sometimes gives the player the appearance of phasing through objects, which’d technically count as bug, however it took me remaking and editing an existing system to get it to work the way we wanted to and not do this, so it counted as a point. Originally I was using animation states that were swapped between when the player was running, sliding, or jumping however this could be broken by the spam if you slide while already sliding in the animation state, I fixed this by instead switching to animation montages pushed to a slot, so if you slide again it’d override the animation and play it again, which thankfully fixed all of our issues.

Apart from all of that, most of what I did this sprint was just adding in meshes and textures, getting them all set up correctly, and bug fixing. There were a LOT of bugs that I had to work on during this sprint, but I managed to get quite a few of them done thankfully, I managed to fix some issues with the boost causing people to die after using it, I fixed a few lighting issues that were causing players to get flashbanged, as well as some issues regarding obstacles and their collision / culling that were causing weird camera and gameplay issues, overall, it wasn’t too high of a point count this sprint, but it was very productive!

Updated Skins:


Now to what I spent most of my time this sprint on, bug fixing. A lot of the bugs we encountered are either rare and hard to reproduce, or are only on the mobile build, both of these creating their own challenges for me and my team to handle. The ones that were hard to recreate had me playtesting a lot trying to fix them, the worst of these was a bug that would very rarely occur that would push the internal view of the lanes to the side, causing the player's movement to not be centered to the lanes of the street mesh, which we’re still in the process of fixing and finding the issue of.

When it comes to the mobile build only issues, we faced quite a few and we’re able to fix most of them, unfortunately I did have to scalp my VHS filter even more, reducing it even more in complexity, since Unreal Engine mobile builds don’t seem to like Post Processing shaders too much. The worst issue we encountered was, only on the mobile build, the player would sometimes start running and moving when they were supposed to, walking off the screen even in the title menu, which we’ve managed to fix for the most part by adding a redundancy boolean.

The issue that they mobile build only bugs were so difficult is that we can’t build to android on my primary workspace, so I’m forced to either wait to get to my laptop at home, or to send it to my produce and have him build, then tell me if my fixes worked, it took a lot longer than I would’ve liked, and multiple build attempts, but eventually we managed to get things fixed!

The final thing I really worked on this sprint was assembly of the house and some of the sound effects, the assembly isn’t very notable as it was essentially using building blocks, but the sound effects were certainly fun to work on. I had a little bit of experience with mixing sound effects before but I assumed I would have a little trouble regardless, and I was right, after first I wasn’t sure where to begin, but after talking to someone I know who gave me some advice, I decided to pick a random noise and edit it to be the kind of sound I wanted, which gave me a lot of freedom to work with, I took a completely different and unrelated noise (In this instance the CAASP testing audio cue) and edited it to be completely unrecognizable and fit what I needed, it taught my quite a lot about sound design and I enjoyed it a lot!

Sprint #3

Our third sprint may be our most productive sprint yet, I managed to get 27 points done, I was hoping to get to 30 but had a little bit of trouble on a 3 point card at the end so I didn’t get around to it

Something I spent a lot of time on this sprint was getting animations set up, we’ve been getting a lot coming in from our Animator so I’ve had a lot to work with and experiment with. I had a bit of knowledge of Animation Graphs and State Machines, but I managed to learn quite a bit more this time around, I even managed to learn something I couldn’t figure out during my Lethal Company project, which was how to push animations to only certain parts of the body, like being able to play idle, attacking, holding, etc on the upper body while the lower body continues to move and run, which is very helpful for this project and future ones. I also taught myself about animation slots and montages, overall I learned a lot and have a newfound respect for riggers and especially people who name the bones in their rigs!

Something I did that I think came out really well has to be the skin menu. We realized that with our current scope, we had time to add in more features so we decided to make player skins, it was a fun system to get implemented, and working on the UI for it made me realise that even though I’m a programmer I could also definitely see myself as a UI Designer, it is pretty fun and I’ve loved how all the UI for this game turned out and I could definitely see myself doing it professionally.

Skins Menu:


Another thing that turned out really well was the quicktime event when being caught by The Strainer, when you’re caught, if you have level 1, 2, or 3 of the Escape upgrades, you have a chance to escape from the strainer 1, 2, or 3 times respectively. Normal, when you’re caught, you just die, but with these perks, you can do a spam click quicktime event to break away from him and continue your run, which serves to really make the player feel like they are stronger and that their upgrades actually have a real effect on their runs, especially since the LVL 1 Escape Upgrade is one of the first ones you can buy!

Strainer Quicktime Event:

Overall we’ve had a really good sprint, and all of the programming for the game SHOULD be finished this sprint, which’ll have me most likely doing some texturing & level design work moving forward after this, which I’ve already started to dabble into, all in all, our game is coming along great so far!

For our second sprint, we’ve again managed to get a lot done. Over the course of this sprint, I got quite a bit done, a lot of which I’ve very proud of; The Upgrade Tree, Implementation of Every Upgrade, Description Pages of every Upgrade, Speed Increased, Falling Light Poles, The beginnings of the Enemy, The Main Title Screen, Working Settings, The Introductory Cutscene, and the code behind the animation states for the Enemy! The three point card I did, which definitely took a lot of time, was the upgrade tree, and that isn’t even counting the implementation of all the upgrades, some of which are fairly complex, like the boost upgrade, which unlocks a boost for the player. The upgrade tree is a large, easily expandable tree that the player can drag around, and each upgrade can be held to pull up a description page of them, showing the name, description, and price!

Upgrade Tree:


Something I worked on that was very new to me was the settings menu, it sounds pretty easy, but setting up sliders for volume and brightness is something I’d never done before and had no idea to go about doing, lucky, the sliders built into the Unreal UI were very intuitive, however there still came the problem of actually attaching volumes changes to them. I ended up teaching myself about Sound Classes and Mixes, which when put together, allow to you apply changes to different categories of sounds across the game, which lucky were very easy to attach to the sliders, which I was able to test using free use music online, which I will be changing later when we get finalized music for the game.

Settings Page:


Something I’m very proud of that I got working was the Camera Movement system, I’ve done a few Camera Movement systems before but this is probably my most advanced one, taking placable points around the world and adding all their references to a map, added under keys that can be set in the world, then allowing the camera to interpolate between them using Timeline and Ease nodes, getting a very smooth and easy to program camera system that I had a lot of fun making, it took a decent bit to get it fully working, and it had a few bugs, but thankfully it works perfect now and I’m very proud of it!
